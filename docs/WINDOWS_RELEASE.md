# Windows Release Build

## Read docs/ANDROID_RELEASE.md first

Same underlying limitation: this project was built in a sandbox with
no Flutter SDK and no reachable `storage.googleapis.com`, so nothing
here has ever been compiled — everything is syntax-checked at best.

## Why Windows gets less hand-written scaffolding than Android did

For Android, I could hand-write `build.gradle`/`AndroidManifest.xml`
and actually *validate* them — Gradle files are declarative enough to
brace-check, and XML has a real parser I could run. Windows desktop's
platform folder is mostly generated Win32/CMake **C++** source
(`runner/main.cpp`, `flutter_window.cpp`, `win32_window.cpp`, resource
files, a `.rc` file with version info, an app icon `.ico`) — code I
cannot compile or meaningfully verify here. Hand-transcribing that
from memory and calling it done would be worse than not writing it:
wrong Win32 boilerplate fails in ways that are much harder to debug
than a missing XML tag, and it would look finished without being
verified at all.

So this phase writes only the top-level `windows/CMakeLists.txt`
(declarative, low-risk, included) and stops there — the honest choice
given what actually can and can't be checked in this environment.

## What to actually do

On a machine with a working Flutter install (confirm with
`flutter doctor` — Windows desktop needs Visual Studio 2022 with the
"Desktop development with C++" workload):

```bash
cd frontend/mindora_app
flutter create --platforms=windows .
```

This is safe to run against this existing project: Flutter's own
tooling only fills in the missing `windows/runner/` C++ files and
`windows/flutter/` generated glue — it does not touch `lib/`,
`pubspec.yaml`, or anything else already written. It's the same
official template every Flutter Windows app uses, generated
deterministically from your project name, so there's no reason to
hand-roll it once a real Flutter install is available.

Then:
```bash
flutter pub get
flutter build windows --release
```

Output lands at `build/windows/x64/runner/Release/` — that whole
folder is the distributable app (the `.exe` plus its required DLLs).
For actual distribution beyond copying that folder, look at MSIX
packaging (`msix` package) or an installer tool like Inno Setup —
neither is configured here, since that's a packaging decision better
made once there's a real signed build to package.

## Sanity-check before distributing anywhere
- Run the `.exe` and click through onboarding, login, and one AI chat
  message — same first-real-runtime-test situation as Android
- Confirm the window icon and title show real branding, not Flutter's
  default (Windows icon comes from `windows/runner/resources/app_icon.ico`,
  generated by `flutter_launcher_icons` if configured for Windows, or
  swap it by hand)
- Voice/vision (Phase 13) were built and tested against mobile
  camera/microphone plugins — verify those plugins' Windows support
  specifically; some Flutter plugins are mobile-only and may need a
  platform-specific fallback or graceful disablement on desktop
